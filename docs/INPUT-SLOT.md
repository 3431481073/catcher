### 一、Lattice 数据口（唯一的对外输入）

#### 1.1 四格

| 格 | 内容 |
| --- | --- |
| **我从哪拿** | **池子在哪**：发现文件 **`~/.lattice/api/current.json`**，读它里面的 `baseUrl`（形如 `http://127.0.0.1:44775`）。<br>走的是**它自己公布的 HTTP 数据口** —— **不 import 它的包、不读它的源码、不直读它的数据文件**。 |
| **拿了什么** | 它**每个窗格的状态与屏幕内容**、以及**变更事件**。见 §1.3 的 9 条。 |
| **拿来干嘛** | 原样转发给**安卓端的「远程」Tab**（手机在外面看/操作电脑上的 Claude Code）。<br>后端只做三件事：找到端口、转发、把上游错误翻成剪藏的错误码。 |
| **我假设它是什么样** | ① Lattice 在跑；② 端口**每次都要重读发现文件**（它是随机的）；③ `baseUrl` 必须是回环；<br>④ 写请求要 `Content-Type: application/json` 且**不能带 `Origin`**；⑤ 它的 SSE 连接数上限是 8。<br>🔴 **不满足会怎样**：**响亮** —— 后端回 `LATTICE_UNAVAILABLE(503)`，手机端显示「后端连不上电脑上的 Lattice：…」。<br>**只有「远程」Tab 坏**，记录/语音/文本这三个入口**一点不受影响**。（逐条展开见 §二） |

#### 1.2 端口是随机的高位端口 —— 靠【发现文件】找

| 项 | 值 |
| --- | --- |
| **发现文件** | `~/.lattice/api/current.json` |
| **可覆盖** | ✅ 环境变量 `LATTICE_HOME`（**测试能离线跑就靠它**，把路径指到 tmp） |
| **读什么** | `baseUrl`，形如 `http://127.0.0.1:44775` |
| **🔴 每次请求都重读** | **不做进程内缓存** —— Lattice 每次启动端口都可能不同（44770 起 12 次尝试）。<br>写死端口或长缓存 = 制造"指着死端口"的 bug。 |
| **🔴 只认回环** | `baseUrl` **必须**以 `http://127.0.0.1:` 开头，否则一律拒。<br>理由：发现文件是**用户可写的普通文件**，Lattice 的 Host 守卫只管它自己那侧 —— 我们这侧再夹一道，保证**永远不拿这个文件里的地址去请求别的机器**。 |

**Lattice 重启会换端口 + 换 runId + 换窗格 id** —— 这是实测过的真事
（2026-10-09：端口 44772 → 44775，窗格 `pane-65` → `pane-1/3/4/5`）。
**后果**：手机端 `prefs` 里记着的窗格 id 会失效 —— 已做「自动重选到焦点窗格」的兜底。

#### 1.3 拿的是哪 9 条

| # | Lattice 的接口 | catcher 的转发路由 | 用途 |
| ---: | --- | --- | --- |
| 1 | `GET /v1/health` | `GET /api/v1/lattice/health` | 探活（返回里带 `runId`，确认控的是哪个实例） |
| 2 | `GET /v1/panes` | `GET /api/v1/lattice/panes` | 窗格列表 + 每个窗格的状态与数据 |
| 3 | `GET /v1/panes/{ref}/status` | 同名 | 单个窗格的状态 |
| 4 | `GET /v1/panes/{ref}/text` | 同名 | 屏幕快照（`mode=screen\|tail\|all`） |
| 5 | `GET /v1/panes/{ref}/last-turn` | 同名 | 最后一轮汇总文本（"📋 复制"用） |
| 6 | 🔴 `POST /v1/panes/{ref}/input` | 同名 | **往窗格写字/按键**（= 在电脑上敲键盘） |
| 7 | `POST /v1/panes/{ref}/answer` | 同名 | 替用户答确认框 |
| 8 | `POST /v1/watch` | 同名 | 声明"我要应答"（不声明 → 钩子 fail-open，问题直接弹电脑上） |
| 9 | 🔴 `GET /v1/events`（**SSE**） | `WS /api/v1/lattice/ws` | 变更事件流 |

> 🔴 **第 9 条的形态要特别说明**：上游是 **SSE**，但**对手机是 WebSocket**。
> 原因实测过：**SSE 穿 Cloudflare Tunnel 会在 10~100 秒之间被不可预测地掐断**
> （两轮 88.8s / 96.9s），而**同一条隧道上 WS 两轮都挂满了 299 秒**。
> 后端因此还兼职"上游断了自动重连、不关手机那条 WS"。
> ⚠️ 中间**短暂存在过**一条 SSE 转发路由（`/api/v1/lattice/events`），**已删**。

#### 1.4 超时（`config.py`，全部可用环境变量覆盖）

| 项 | 默认 | 环境变量 |
| --- | --- | --- |
| 连接 | **2s** | `CLIP_LATTICE_CONNECT_TIMEOUT` |
| 读 | **10s** | `CLIP_LATTICE_READ_TIMEOUT` |
| 写 | **5s** | `CLIP_LATTICE_WRITE_TIMEOUT` |
| 事件流的读 | **不设**（`read=None`） | —— |

**为什么要分两套**：普通请求要短超时（Lattice 卡死时不能让手机请求堆积）；
**事件流必须不设读超时**，否则 **10 秒就被自己的超时掐死**，而 Lattice 的心跳是 20 秒一次。

#### 1.5 一个不显然的耦合：`enter` 被拆成两次写

Lattice 收到 `enter:true` 时会把**文字和 `\r` 拼成一个 chunk 一次写进 PTY**，
实测这样发出去的指令**会停在 Claude Code 输入框里不提交**。
所以后端把它**拆成两次独立的 Lattice 调用**（中间隔 200ms），让 PTY 上是两次读。

> 这是本组接口里**唯一一条"有脑子"的、不是纯透传**的。写在 `routes\lattice.py` 的注释里。

### 二、我假设它是什么样

> **它必须满足什么** —— 下面每条不满足时都会**响亮报错**（对应 §1.1 第四格）。

| # | 假设 | 不满足会怎样 |
| ---: | --- | --- |
| 1 | **`current.json` 存在且是合法 JSON** | `LATTICE_UNAVAILABLE(503)`："电脑上的 Lattice 没在运行" |
| 2 | **`baseUrl` 以 `http://127.0.0.1:` 开头** | 同上，且**绝不会**请求到别的机器 |
| 3 | **写请求必须 `Content-Type: application/json`，且不带 `Origin`** | Lattice 回 415/403 → 翻成 `INVALID_PAYLOAD` / `SERVER_ERROR` |
| 4 | **窗格 `ref` 只接受 `pane-N` 这种裸写法**（不含斜杠） | `INVALID_PAYLOAD(400)`。<br>🔴 带斜杠的 `runId/pane-N` **故意不支持** —— 拼 runId 只会在 Lattice 重启换 runId 后静默指向新实例的同名窗格，裸 ref 的语义才天然正确。 |
| 5 | **SSE 连接数 ≤ 8** | 超了 Lattice 回 503 → 翻成 `LATTICE_UNAVAILABLE`。（我们只占 1 条） |

🔴 **整体坏掉的样子**：后端回 `LATTICE_UNAVAILABLE(503)`，
手机端显示「后端连不上电脑上的 Lattice：…」——
**只有「远程」Tab 坏**，记录 / 语音 / 文本这三个入口**一点不受影响**。
