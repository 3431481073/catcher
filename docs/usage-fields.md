# App 使用时长：字段清单

> **面向外部读者**（`snapshot` 等消费方）。**内部实现**见 [`architecture.md`](architecture.md) §10.8。
> **本文只讲"库里有什么、每个字段什么意思"**；**怎么读**见 [`usage-read.md`](usage-read.md)；一条真实数据见 [`usage-sample.json`](usage-sample.json)。
>
> 建立于 **2026-10-12**。**下面前三个数是那一刻的快照，不是常量**（实测几分钟内就从 7,154 涨到 7,158）：
> `usage_records` **7,158 行** · 跨度 `2026-10-04T12:24:38Z` ~ `2026-10-11T19:35:48Z` · **一台设备**。

## 一、两张表在哪

**都在 catcher 后端那一个库里**（SQLite，WAL 模式），**没有单独的库文件**：

```
D:\MyProject\catcher\backend\dist\data\app.db
```

| 表 | 一句话 | 谁写 |
| --- | --- | --- |
| **`usage_records`** | **配对好的"使用段"** —— 这是主要读的一张 | 后端（手机只上报原始事件） |
| **`usage_pending`** | **每设备一行，记"还没结束的那一段"** | 后端 |

> 🔴 **`usage_pending` 不是给消费者用的。** 它只是配对过程中的中间状态，**读它没有业务意义**（见第三节）。**要算时长、要排行、要按天统计，一律读 `usage_records`。**

## 二、`usage_records` —— 主表

### 2.1 字段

| 字段 | 类型 | 可空 | 语义（面向外部读者） |
| --- | --- | --- | --- |
| **`id`** | TEXT | 否 | 行标识，格式 `usage_` + 32 位十六进制。**对消费者没有意义**，只用于唯一标识这一行。⚠️ **同一段被覆盖时 id 不变**（`DO UPDATE SET` 里没有它）—— 不要拿它当"这行变没变"的判据 |
| **`device_id`** | TEXT | 否 | **哪台设备**。是 Android `ANDROID_ID` 的 **SHA256 前 16 位十六进制**。同一台手机卸载重装**不变** |
| **`package_name`** | TEXT | 否 | **哪个 App**，Android 包名（如 `com.tencent.mm`）。**这是跟 App 对应的稳定标识** |
| **`app_label`** | TEXT | **是** | **App 的可读名**（如 `微信`）。⚠️ **可空** —— 只有在"手机上报的那一批事件里出现过这个包名"时才会有值；一般为空的情况极少（见 §6.4） |
| **`start_time`** | TEXT | 否 | **这一段从什么时候开始**。格式与精度见 §4 |
| **`end_time`** | TEXT | 否 | **这一段到什么时候结束** |
| **`duration_seconds`** | INTEGER | 否 | **这一段持续了多少秒** = `(end_time − start_time)` **向下取整到整秒**。⚠️ **它是存下来的，不是算出来的** —— 消费者可以直接求和，**但要注意向下取整会让每一段少 0~1 秒**（见 §6.2） |
| **`created_at`** | TEXT | 否 | **这行是什么时候被写进库的**（**不是使用时间**）。ISO8601 UTC，微秒 |
| **`updated_at`** | TEXT | 否 | **这行最后一次被改写的时间**。⚠️ **它可能远晚于 `created_at`** —— 同一段被重复上报时会**原地覆盖**（见 §6.3） |

> ✅ **HTTP 接口返回的字段和 sqlite 的表字段【完全一致】，各 9 个**（2026-10-12 实测）。
> 接口原来只给 7 个（少了 `created_at` / `updated_at`），那天补上了 —— **消费方不必为了这两个字段再直读库。**
>
> **那两个后加的字段是什么**（都不是使用时间，别拿去算时长）：
>
> | 字段 | 一句话 | 什么时候会变 |
> | --- | --- | --- |
> | `created_at` | 这条段**第一次被写进库**的时刻 | **不变**（除非整行被删了重写） |
> | `updated_at` | 这条段**最后一次被改写**的时刻 | **会变** —— 同一段被重复上报时走唯一键原地覆盖。⚠️ **它变的时候 `start_time` / `end_time` / `duration_seconds` 可能一个字都没变**，所以**别拿它当"要不要重新拉"的判据** |

### 2.2 唯一键与索引（实测自库）

```sql
-- 🔴 唯一键 = 一段的"身份"
CREATE UNIQUE INDEX ux_usage_seg
  ON usage_records(device_id, package_name, start_time);

CREATE INDEX idx_usage_start ON usage_records(start_time);
```

**`ux_usage_seg` 的含义**：**同一台设备 + 同一个包名 + 同一个起点 = 同一段**。
**⇒ 重复上报不会让行数变多**，只会覆盖 `end_time` / `duration_seconds` / `updated_at`。
**⇒ 消费方可以放心地反复读，不会读到"重复的两行"。**

**`idx_usage_start`** 是给"按时间区间查"用的。**按 `start_time` 过滤时能走索引。**

## 三、`usage_pending` —— 进行中的那一段（**消费者不用读**）

| 字段 | 类型 | 可空 | 语义 |
| --- | --- | --- | --- |
| **`device_id`** | TEXT | **主键** | 哪台设备。**每设备最多一行**。（SQLite 的 `TEXT PRIMARY KEY` 语法上允许 NULL，但实际总会有值） |
| **`package_name`** | TEXT | 否 | 当前这个还开着的是哪个 App |
| **`start_time`** | TEXT | 否 | 它从什么时候开始 |
| **`updated_at`** | TEXT | 否 | 最后一次被哪个批次碰过 |

**它为什么存在**：配对要**跨批**。手机每隔几分钟才上报一次，而"用户现在正在用的那个 App，这一段还没结束"—— 这个状态必须活过两次上报之间（后端会被服务管理器重启，**放内存里一重启就丢**）。

> 🔴 **看到的 `start_time` 可能是很久以前的** —— 那表示"从那时起一直没换过 App / 没锁屏"，**不是数据坏了**。
> 🔴 **要读时长请读 `usage_records`。**

## 四、时间的格式与精度

**所有时间字段都是同一个格式**（`start_time` / `end_time` / `created_at` / `updated_at` / `usage_pending` 的两个）：

```
2026-10-11T19:34:14.207000Z
^^^^-^^-^^ ^^:^^:^^.^^^^^^ ^
  日期      时:分:秒 微秒  UTC 标记
```

| 项 | 值 |
| --- | --- |
| **标准** | ISO 8601 |
| **时区** | **UTC**（结尾的 `Z`） |
| **精度** | **微秒（小数点后 6 位）** |
| **宽度** | **定宽**（29 个字符）⇒ 🔴 **可以直接当字符串比较大小**，`>=` / `<` / `BETWEEN` 都等价于时间比较，**不需要解析** |

### 🔴 时区换算（最容易出错的一步）

**库里全是 UTC，而"哪一天"是本地概念。**

- **`start_time` 的日期部分 ≠ 用户以为的那一天。** 例如 `2026-10-11T19:34:14Z` 对 **UTC+8** 的用户来说是 **10-12 的 03:34**。
- **HTTP 接口的 `date=` 参数按【服务器本地时区】解释**（这台服务器就是 UTC+8，和手机一致），**返回的仍是 UTC**。见 [`usage-read.md`](usage-read.md)。

**⇒ 直读库时，想按"本地某一天"筛，必须自己换算**：

```sql
-- 本地(UTC+8) 的 2026-10-11 一整天  →  UTC 2026-10-10T16:00Z ~ 2026-10-11T16:00Z
SELECT * FROM usage_records
WHERE start_time >= '2026-10-10T16:00:00.000000Z'
  AND start_time <  '2026-10-11T16:00:00.000000Z';
```

**⇒ 过滤的是【段的起点】不是"与区间有交叠"**：一个 23:50→次日 00:20 的段**整个算在前一天**。这样每段只归一天，**跨天不会重复计数**（见 §6.1）。

## 五、需求单第九节的五个疑问 —— 逐条答复

### 1. 能不能拿到 `UsageStatsManager` 的数据？—— **能，但要一个特殊权限**

| | |
| --- | --- |
| **要什么** | **`PACKAGE_USAGE_STATS`** —— 这是**特殊权限（AppOps）**，**不在普通权限列表里**：声明它不会弹授权框，`requestPermissions` 对它无效 |
| **怎么授** | 用户手动去 *设置 → 应用 → 特殊应用权限 → 使用情况访问*，给「剪藏」打开开关 |
| **怎么查** | `AppOpsManager.unsafeCheckOpNoThrow(OPSTR_GET_USAGE_STATS, uid, pkg)`（**不是** `checkPermission`，那个对它永远返回 DENIED） |
| **拿不到会怎样** | **一条数据都没有**，而且**是静默的**。App 侧因此在记录页顶部挂了一条可关闭的提示 |
| **还用了什么** | `QUERY_ALL_PACKAGES`（Android 11+ 拿别的 App 的**可读名**用）。**没有它包名照样有**，只是 `app_label` 为空 |

### 2. 历史范围能回溯多久？—— **通常 1~7 天，随 ROM 而异**

**`UsageStatsManager.queryEvents` 只保留系统认为"最近的"那一批**，实测在这台设备上能回溯到 **7 天**。

- **首次授权后**：App 会立刻回溯 **7 天**（按天切分，可中断续传）
- 🔴 **App 超过 7~8 天没跑，中间那段【拿不回来】** —— 是系统的保留策略，不是本项目的缺陷
- **各家 ROM 保留时长不同**，本项目没有兜底手段

### 3. 采集方式 —— **定时聚合 + 事件驱动，两路都有**

| 触发 | 频率 | 说明 |
| --- | --- | --- |
| **周期任务**（WorkManager） | **15 分钟**（系统允许的最小值） | 主路径 |
| **App 启动 / 回前台** | 每次 | 排一发即弃的 WorkManager 任务 |
| **`POST /api/v1/usage/trigger`** | 手动 | 后端经 WS 推 `trigger_usage` 给手机。⚠️ **只在手机开着「远程」Tab 时收得到** |
| **用户从最近任务划掉 App** | 一次 | 尽力采一次（进程要死了，成不成看系统） |

**⇒ 拉取区间永远是「上次扫到的时间 − 5 分钟 到 now」** ⇒ **被推迟不会漏**（推迟 3 小时就多拉 3 小时）。
那 5 分钟重叠是留给"正好跨在两次扫描之间"的段的 —— **宁可重复（两端都去重），不能漏**。

### 4. 数据保留 —— **永久，不自动清理**

后端**没有任何清理策略**：不按时间删、不按条数删、不 VACUUM。
**要删只能人工动库。**（`usage_records` 目前约 **7 千行 / 11 天**，量级很小。）

### 5. 有没有别的采集方冲突？—— **没有，是独立的两张表**

- 这两张表**只被 App 使用时长采集这一条链路写**，没有第二个写入方
- **它们和 `records` / `tasks` / `events` 完全独立**（那是剪藏记录/转写任务/事件旁路的表）
- **列名一个字都没动过那三张表** —— `video-workbench` / `video-panel` 在逐字引用它们（见 [`deps.md`](deps.md) §一）

## 六、四个"看起来像 bug、其实不是"的行为

### 6.1 一个段**不会被算进两天**

分段时**按段的起点归属**。一个 23:50 → 次日 00:20 的段，**整体算在前一天**，后一天查不到它。
**⇒ 好处：每段只计一次，跨天求和不会重复。** 代价：那一天的头 20 分钟看起来是空的。

### 6.2 `duration_seconds` 是**向下取整**，逐段求和会少几秒

`(end_time − start_time)` 取整到秒。实测：`19:34:14.207 → 19:34:56.620` = **42.413 秒** → 存 **42**。

**⇒ 段数多的时候，逐段求和能比"实际时长"少 0~1 秒 × 段数。** 一天上千段 ⇒ **最多少十几分钟**。
**要精确求和，用 `end_time − start_time` 自己算**（两者都是定宽 ISO 串，在 SQLite 里能用 `julianday()` 或直接字符串解析）。

### 6.3 `updated_at` 可能远晚于 `created_at` —— 那是**重复上报的原地覆盖**，不是新数据

同一段被重复上报时，唯一键命中 ⇒ **覆盖**（这正是为"上次扫描被窗口截断、这次拿到完整的"设计的）。
**实测过一次整库 94% 的行被重写**（手机侧重传了整个 7 天）。
**⇒ 判断"要不要重新拉"不要看 `updated_at`，要看 `start_time` / `end_time` 有没有变。**

### 6.4 `app_label` 什么时候会是空的

只有"手机上报的那一批事件里出现过这个包名"时才会有值。所以：
- **正常情况**：包名一出现，同批就带上了名字 ⇒ 不为空
- **为空**：App 已卸载、包名不可见（没声明 `QUERY_ALL_PACKAGES` 的机型）、或该包名只在**老数据**里出现过而后续批次没再报

**⇒ 消费方应当把 `app_label` 当"提示"而不是"权威"**：**跟 App 对应请用 `package_name`**，显示给人看时 `app_label` 为空则回退到包名。

### 6.5 超过 6 小时的段会被**整段丢弃**

后端有一道兜底：单段 `duration_seconds > 21600`（6 小时）⇒ **不写库**，计数上报（`oversized_skipped`）。
它是防"上游数据已经被污染"用的（实测出现过一次起点被拖到 34 小时前的 `usage_pending`）。
**现有真实数据里最长的一段是 2.98 小时（快手）**，所以正常使用**不会触发**。
